# 裁判文书论证结构标记系统 · 项目说明

> 给协作开发者的交接说明。重点讲**需求**和**架构**，不展开实现细节。
> 需求细节以 `需求/需求文档-V0.1.1.md` 与 `需求/pdf_text.txt`（指南 v1.1 全文）为准；本文是两者的浓缩 + 我们讨论后形成的共识。

---

## 1. 一句话定位

对裁判文书的**裁判理由**部分做**论证结构的结构化标注与图示**：把自然语言里的推理过程拆成命题、给命题分类、标注命题之间的论证关系，并自动生成论证图；在此基础上沉淀可训练的数据集，并提供一个面向课堂的教学练习系统。

服务两类场景：

- **正式标注生产**（法学研究团队协作标注、裁定、导出数据集）
- **教学辅助**（教师发布练习、学生练习标注、系统比对标准答案）

---

## 2. 业务目标

1. **论证挖掘与结构化**：从裁判文书中提取命题与结论，标注命题类型与命题间关系。
2. **可视化**：按统一规范自动生成论证图示。
3. **数据沉淀**：形成可复用、可追溯的论证结构数据集，供模型训练与评估。
4. **教学辅助**：提升学生学习法律论证模型的效率与效果；帮助教师掌握学习情况并针对性发布练习。

---

## 3. 系统总览

系统拆成两个独立系统，**入口并列**：

```
index.html（唯一入口）
│
├─ [ 标注系统 ]  labeling.html      正式标注生产
│      ↓
│   登录（邮箱 + 密码）
│      ↓
│   团体层：创建团体 / 凭身份码申请加入 / 切换团体
│      ↓
│   工作界面（侧边栏按团内身份动态渲染）
│
└─ [ 教学系统 ]  teaching.html      学生练习平台
       ↓
    登录（邮箱 + 密码）
       ↓
    班级层：创建班级 / 凭班级码加入 / 切换班级
       ↓
    工作界面（老师 / 学生两套导航）
```

**两个系统分开管**：各自一套账号、一套登录页、一套外壳与导航、一套浏览器存储。底层领域引擎（形式化表达解析、图示渲染、标注数据结构）共用。

## 4. 标注系统需求

### 4.1 账号

- 账号 = 一个人，**本身不含任何业务权限**。
- 登录标识以邮箱为主，手机号可选。
- 自助注册 + **开发维护方审核**（系统外角色，原型只呈现「等待审核」状态）。

### 4.2 团体

- 团体是标注工作的单位，也是**数据边界**：文书、任务、标注结果全部挂在团体上，团体之间互相不可见。
- **创建**：任何登录用户都可创建，创建者成为该团体的**最高管理**。
- **加入**：输入**身份码** → 提交申请 → 该团体管理员审核通过。
- 一个人可属多团、可管多团；工作界面内常驻「团体管理」，可随时切换、新建、加入。

### 4.3 团内身份

身份**逐团体**成立，由管理员指定，本人不能自选。

| 身份 | 说明 |
|---|---|
| 最高管理 | 创建者默认获得。比普通管理员多：转交管理权限、解散团体、移除管理员 |
| 管理员 | 由最高管理指定，可多人，权限与最高管理基本相同 |
| 标注员 | 由管理员指定 |
| 裁定员 | 由管理员指定 |

- 被指定身份后自动获得对应功能；管理员推送的任务自动出现在本人列表。
- **管理员可以给自己也授予标注员 / 裁定员身份**，否则进不了标注区 / 裁定区。
- 待定：普通管理员能否罢免另一个管理员。

### 4.4 侧边栏

按「我在当前团体有哪些身份」动态渲染，切团后随之变化。

```
概览
管理区   ← 最高管理 / 管理员
  文书与语料 · 标签体系 · 任务创建与分配 · 成员与身份 · 结果输出
标注区   ← 标注员
  我的任务
裁定区   ← 裁定员
  待裁定 · 已定稿
```

标注工作台是从「我的任务」点进去的**下钻页**，不占侧边栏条目。

### 4.5 任务模型

任务是一个**管理单位**（一个「筐」），文章数量不限（1 篇到 N 篇）。

- **细分指派**：管理员指定谁标哪几篇；**没有指定的就没有任务**。
- 指派可在任务创建后变更。
- 裁定员按任务指定（不是公共池）。
- 截止日期：任务上有一个统一 ddl，每篇文档可单独覆盖。
- 「阶段 01 创建 / 02 标注 / 03 裁定 / 04 输出」挂在任务上。

### 4.6 标注工作台

三栏：**原文 / 命题与标签 / 论证图示 + 关系区**。

- **颗粒度对齐**：按句号自动给出切割建议，过渡语词并入其后第一个要素；逐段确认后转为要素。
- **要素标注**：在原文中选中文字即创建命题并自动分配序号；可先给序号、标签稍后给出。
- **关系标注**：在图中按住 Shift 拖动一个图元到另一个图元建立 S / A / M；Ctrl 多选后建 J / I；也可手动输入形式化表达。
- **图示**：随标注实时成图，支持拖拽布局、缩放平移；序号按原文顺序动态重排，关系引用随之重映射。
- 容错方式：**删除 — 重新创建**，不做撤销栈。

### 4.7 裁定与导出

- 裁定者并排查看多个标注版本，逐条选择认可哪一份，或直接重标；**系统不自动比对差异所在**，由裁定者人工比对。
- 只有一种标注版本时同样展示该界面。
- 定稿后任务进入阶段四，不可回退。
- 导出：图示 PNG / JPG / SVG；数据 Excel（实现为 CSV）/ JSON。导出数据不加密、不加水印。
- 结果查看显示所用指南版本。

## 5. 教学系统需求

### 5.1 班级

- 一个班级只有**老师**和**学生**两种身份。
- 老师可带多个班，学生可加多个班。
- 加入：**输入班级码即入，不审核**。

### 5.2 老师侧

| 功能 | 说明 |
|---|---|
| 文档库 | 上传裁判文书 |
| 标准答案 | 用**同一套标注界面**为文档标出标准答案 |
| 练习 | 发一次练习 = 选一批文档 + 定 ddl + 可选「到期自动发布答案」 + 选择面向全班或指定学生 + 标注「针对类型」 |
| 成员 | 班级码、学生名单 |
| 统计 | 每次练习的完成人数、未完成名单、平均相似率、相似率排行 |

### 5.3 学生侧

- 凭班级码加入班级。
- 在练习中**逐篇标注、逐篇提交**；提交可重复，第一次提交即视为完成。
- 学生做的是**完整标注**：命题 + 标签 + 关系，使用与标注系统**同一套三栏工作台**。
- **查看答案的条件**：该篇本人已提交 **且** 老师已发布答案。
- 查看自己的相似率。

### 5.4 相似率

- 只用一个指标，衡量学生结果与标准答案的重合度，**覆盖命题、标签、关系**。
- 具体核算方式留给后端；原型前端用简单重合度顶替（命题覆盖 30% + 标签正确 40% + 关系重合 30%）。

## 6. 领域模型（指南 v1.1）——整个系统的地基

> 这部分最容易被漏，但它是标注、图示、比对、导出的共同基础。

### 6.1 标注对象与范围

- 对象：裁判文书的**裁判理由**部分。
- 原始判决书：自「本院认为」起，至「判决如下」所在句子之前。
- 指导性案例 / 参考案例：「裁判理由」段落。

### 6.2 颗粒度

1. 以**句号**为单位第一次切割。
2. 句内以**逗号、分号**考查子句。
3. 连续子句若同性质且无明显支持/反对关系 → 合并为一个要素，占一个序号。
4. 异性质或存在明显关系 → 分开标注。
5. 带双引号的内容，以双引号为单位。
6. **所有过渡语词**（「因此，」「综上来看，」等）并入其后第一个要素。

### 6.3 要素类型

**非命题层**

| 代码 | 名称 |
|---|---|
| IS | 争议焦点 |
| Non | 非论证成分 |

**命题层**：两个维度 × 两层 = 四类基础判断

|  | 个别 | 一般 |
|---|---|---|
| 事实 | SF 个别事实判断 | GF 一般事实判断 |
| 规范 | SM 个别规范判断 | GM 一般规范判断 |

**GM 的五个子类**：GM-L 法律条文、GM-I 法律解释、GM-U 习惯与行业惯例、GM-M 道德与价值观念、GM-O 其他规范判断。

**SM 的子类型**：普通个别规范判断仍记为 **SM**；合同及对合同条款的规范性解释单列为 **SM-C**（注意：合同归 SM 下，不是 GM）。

### 6.4 关系类型（五种）

| 代码 | 名称 | 形式 | 图示 |
|---|---|---|---|
| S | 支持 | S(pi, pj) | 实心圆 ● + 有向边 |
| A | 反对 | A(po, pc) | 空心圆 ○ + 有向边 |
| J | 组合 | J(p1…pn) | 带「+」圆 ⊕ + 无向连线 |
| M | 匹配 | M(ps, pg) | 带「+」圆 ⊕ + 有向边 |
| I | 同一 | I(p1…pn) | 矩形框内「/」，无关系节点 |

### 6.5 嵌套结构（六种）

```
M(J(ps1, ps2, …, psn), pg)          组合内嵌于匹配
J(M1, M2, …, Mn)                    匹配内嵌于组合
S(J(pi1, …, pin), pj)               组合内嵌于支持
S(M(ps, pg), pj)                    匹配内嵌于支持
A(po, S(pi, pj))                    支持内嵌于反对
S(M(J(p1, p2, p3), p4), p5)         多层嵌套
```

关系用**术语树**表达：`{ t:'S', c:[ … ] }`，子项是 `{ p:'P4' }` 或另一棵术语树。这是前后端、图示、导出共用的核心数据结构。

### 6.6 图示规则

- 命题节点 = **矩形**，框内只写序号，**不携带类型信息**。
- 关系节点 = **圆形**：实心 ● 支持、空心 ○ 反对、带「+」⊕ 组合/匹配。
- 同一关系以矩形框内「/」表示，不设关系节点。
- 嵌套自内而外逐层构造，保持各层关系节点独立。

### 6.7 命题角色

前提 / 子结论 / 结论**不作为独立标注项**，由关系结构自动推导（入度/出度分析）。

### 6.8 冲突处理

两份需求文档冲突时，**一律以指南（PDF）为准**。已知冲突：需求文档把合同写作 GM-C，指南是 **SM-C**；需求文档只列四个一级标签，指南另有 IS / Non。

## 7. 架构与代码组织

### 7.1 原型现状（纯前端）

```
prototype/
  index.html            入口页：选系统
  labeling.html         标注系统外壳：登录 → 团体 → 工作界面
  teaching.html         教学系统外壳：登录 → 班级 → 工作界面

  assets/css/           tokens / base / auth / shell / components / pages / systems / entry
  assets/js/
    core/               data · text · formal · graph · diagram · ui
    shared/             workbench.js   三栏标注工作台（两系统共用）
    labeling/           store · app · pages/（9 个页面）
    teaching/           store · app · pages/（9 个页面）
```

**分层意图**：

| 层 | 职责 |
|---|---|
| `core/data` | 标签体系与语料（指南 v1.1 的代码化） |
| `core/text` | 颗粒度切分、字符定位、要素重排、相似度 |
| `core/formal` | 形式化表达的解析 / 打印 / 校验 / 命题角色推导 |
| `core/graph` | 关系树 → 分层图（§6 的构造规则） |
| `core/diagram` | SVG 渲染（图元规范） |
| `shared/workbench` | 三栏工作台，只依赖 core + 一个配置对象，两个系统复用 |
| `labeling|teaching/store` | 各系统的状态与业务规则 |
| `labeling|teaching/app` | 各系统的路由、权限、外壳 |
| `pages/` | 页面渲染 |

**关键设计**：`workbench` 不直接依赖任一系统的 store，通过 `{ doc, model, save, onSubmit, answer, ... }` 配置接入。因此教学系统能原样复用标注系统的标注能力。

### 7.2 目标系统（给协作开发）

原型是纯前端演示，正式系统需要后端。建议的切分：

- **领域内核可原样移植**：`core/formal`、`core/graph`、`core/diagram`、`core/text` 与具体存储无关，前后端都可以复用（后端可用同一套规则做校验与导出）。
- **store → API**：`labeling/store.js` 与 `teaching/store.js` 里的方法边界，基本就是后端接口清单。
- **权限在后端落实**：团内身份、任务指派、答案可见条件，都必须在服务端校验；前端的隐藏只是体验。
- **相似率算法**放后端，前端只展示数值。
- **文件解析**（PDF / Word）放后端；原型不做。

### 7.3 两套数据模型（目标模型，原型已实现其中大部分）

**标注系统**

```
accounts[]                平台账号
teams[]                   团体（ownerId、inviteCode、members[{accountId, roles}]、joinRequests）
documents[]               文书（teamId 归属团体）
tasks[]                   任务（teamId、stage、deadline、items[{docId, annotators[], arbiters[], deadline}]）
annotations[]             标注（taskId、docId、accountId、elements[]、relations[]、status）
finals[] / exports[] / log[]
```

**教学系统**

```
accounts[]                另一套账号（老师 / 学生）
classes[]                 班级（classCode、members[{accountId, role}]）
documents[]               文档（classId、answer{elements[], relations[]}）
exercises[]               练习（classId、docIds[]、deadline、autoPublish、published、针对类型*、指定学生*）
                          * 这两项为「针对性发布」的目标需求，原型尚未实现
submissions[]             提交（exerciseId、docId、accountId、elements[]、relations[]、status、similarity）
```

**两边共用的标注数据结构**：

```
命题  { seq, code, sub, text, start, end }
关系  { id, tree, label }
```

## 8. 关键约定与边界

| 项 | 约定 |
|---|---|
| 原型形态 | **纯前端**，无后端、无构建步骤，`file://` 双击可开，数据存 localStorage |
| 需求冲突 | 一律以指南（PDF）为准 |
| 指南版本 | **v1.1**。注意：`需求/` 里那个文件名写着 v1.2 的 PDF 是**误标**，内容就是 v1.1 |
| 文件解析 | 原型不解析 PDF / Word；真实读取 `.txt`，其他格式载入内置语料作等价替代并标明 |
| Excel 导出 | 实现为 `.csv`（带 BOM），不生成 `.xlsx` |
| 注册审核 | 只呈现「等待审核」状态，审核方为开发维护方（系统外） |
| 撤销 | 不做撤销栈，容错方式为「删除 — 重新创建」 |
| 差异比对 | 不自动比对，由裁定者人工比对 |
| 相似率 | 具体算法留后端 |

### 待定项

1. 普通管理员能否罢免另一个管理员
2. 相似率的具体核算方式
3. 老师是否也可参与学生练习的标注
